01

데이터 전처리 파이프라인 설계

크롤링한 올리브영 데이터를 정제해 Silver 레이어에 분기 저장하고, Graph RAG 시스템에 공급하는 ETL 파이프라인입니다.

파이프라인 흐름

S3에 레이어별로 적재합니다.

Bronze카테고리별 올리브영 상품 정보 수집 및 적재
→
Silver정제 및 성분 매칭
Current: 최신 스냅샷 (overwrite)
History: 시계열 누적 (append)
Error: 거부 레코드·잔여 성분 경고를 사유별로 태깅 보존
→
Gold성분별 INCI 정보 매핑, Graph DB 적재용 데이터셋 생성

Error로 분기되는 경우: 크롤링 데이터 누락, 중복 데이터, 성분 분석이 불가한 데이터, 성분 매칭이 안 된 경우

문제

  • 성분 표기가 상품마다 제각각이고, 현행 성분명과 구명칭이 섞여 있다
  • 상품 하나에 성분을 귀속시킬 수 없는 경우가 있다 (옵션 선택형, 이종 결합 세트)

처리

  • Aho-Corasick으로 성분표에서 사전 어휘를 다중 패턴 탐색
  • 성분 현행명과 구명칭을 모두 사전에 두어 표기가 바뀐 성분도 매칭
  • 귀속 불가 상품은 분석 대상에서 제외하되, 버리지 않고 사유를 남김
  • 운영 개선: 과거 누락 배치 재처리를 위한 별도 Backfill 경로 추가
  • 운영 개선: DLQ 자동 재투입 대신 사전 보완. 오류 1,826건 중 82%가 의도된 제외(중복 56%, 번들 26%)이고 3일마다 재수집되므로, 사전만 고치면 다음 배치에서 자동 복구

성분 매칭 정합성 상시 95%+ 유지 (평상 ≈ 99.1%, 95% 미만 시 알람). 실패는 DLQ(Error)로 격리해 파이프라인 무중단

성분 매칭을 Aho-Corasick(사전 2.6만 키)으로 O(n·m) → O(n+m) 개선 → 사전 완전탐색 대비 약 200배대 속도

02

CI/CD: 키리스 인증과 결과를 확인하는 배포

SSM 호출 성공을 배포 성공으로 보지 않도록 결과를 회수하고, 실행 중 태스크를 끊을 수 있는 재시작만 승인을 거치게 했습니다.

구축 배경

DAG 내 스테이지를 독립 컨테이너(DockerOperator)로 끊어 설계 → 코드 변경이 이미지로 반영되어야 실제 실행에 적용되는 구조

  • 이미지: 손으로 하면 4개 레포에 이미지 빌드 후 ECR push를 매번 반복해야 한다
  • 호스트: DAG 정의와 compose 설정은 Git에 있는데, 서버에 직접 붙어 작업하는 일이 잦아 git pull을 빼먹고 실행 코드와 레포지토리가 어긋나는 일이 반복됐다

CI/CD 파이프라인 구성

  • 이미지는 ECR에서, 호스트의 DAG 및 설정은 Git에서 각각 최신을 맞춤
  • 역할을 용도별로 나눠 최소 권한 유지
워크플로우하는 일Assume Role
build-and-push.yml이미지 빌드 → ECR pushGitHubActionsECRRole
deploy.yml (Airflow_Infra)SSM으로 git pull + 결과 회수, compose 변경 시 승인 후 재시작GitHubActionsSSMRole
deploy.yml (Monitoring_Infra)바뀐 설정의 서비스만 재시작 + 헬스체크 3종GitHubActionsSSMRole

키리스 도입

  • 레포 secrets에 액세스 키를 두면 유출 시 회수가 어렵고 주기적 교체가 부담
  • GitHub OIDC로 받은 단기 토큰으로 IAM Role을 assume → 레포에 AWS 키 없이 배포

배포 결과 확인과 위험도별 반영 (2026.10)

  • SSM 호출 성공 ≠ 배포 성공: 원격 git pull이 실패해도 초록불이던 배포를, 결과를 회수해 실패로 처리하도록 변경 → 첫 실행에서 숨어 있던 소유권 문제가 바로 드러나 수정
  • 위험도별 반영: 알림과 수집 설정은 머지 즉시 자동 반영하고, 실행 중 태스크를 끊을 수 있는 scheduler 재시작만 GitHub environment 승인 후 반영
  • 승인 경로 검증: compose에 주석만 바꾼 PR로 감지 → 승인 → 재시작 → 헬스체크 OK. 설정 변화가 없어 scheduler가 재생성되지 않으므로, 태스크 중단 위험 없이 흐름 전체를 확인

※ 최초 SSM 배포는 팀원이 구현했고, 결과 확인과 자동 반영, 승인 분리는 직접 설계했습니다.

03

통합 모니터링

사람이 보고 있지 않아도 증상이 드러나야 한다. 대시보드는 증상을 보이게, 알림은 보지 않을 때 알리게.

흩어진 5개 환경을 한 화면으로

수집 경로는 환경마다 달라도 라벨을 통일해, 지표에서 해당 작업의 로그까지 한 화면에서 이어 봅니다.

문제

  • 실행 환경이 홈서버, EC2, GPU 클라우드, 웹 서버에 흩어져 실패를 알려면 사람이 직접 접속해야 했다
  • DAG가 성공해도 결과가 틀릴 수 있다

무엇을 보이게 만들 것인가

질문관측 대상
파이프라인이 도는가Airflow
결과가 맞는가데이터 정합성
서빙이 정상인가vLLM, 웹 서버
그래프가 채워지는가Neo4j

수집 경로 판단

  • 홈서버는 다른 tailnet이라 push만 가능
  • Airflow EC2는 태스크 로그를 파일로 읽어야 해서 로컬 에이전트(Grafana Alloy)로 push
  • 웹과 vLLM은 자체 /metrics를 노출하므로 기존 pull 유지

경로는 달라도 라벨을 job · host · dag_id · task_id로 통일 → 패널에서 바로 해당 구간 Loki 로그로 이동

그 밖에 바꾼 것

  • ARM(t4g) 한 대로 마이그레이션
  • 끝난 실행만 보이던 StatsD를 보완하려 REST API exporter 추가
  • 팀원 범위: 웹, vLLM의 pull 경로와 Neo4j 플러그인은 팀원 구성을 유지

Airflow 대시보드

끝난 실행의 통계만으로는 멈춘 파이프라인이 보이지 않는다 → 실행 중 상태와 직전 결과, 신선도를 따로 수집해 보이게 했습니다.

문제

  1. StatsD 지표는 끝난 실행의 통계라서 현재 어떤 DAG와 태스크가 얼마나 돌고 있는지, 직전 실행이 어떻게 끝났는지 알 수 없었음
  2. 메트릭이 비었을 때 "실행이 0건"인지 "수집이 끊긴 것"인지 구분할 수 없었음
  3. DAG 선택 변수가 완료 이력 기반이라, 한 번도 안 돈 수동 백필 DAG는 목록에 없음

처리

Airflow REST API를 조회하는 exporter로 패널 6개를 추가했습니다. 기존 StatsD 패널은 지우지 않고 "전체 부하와 추세" 역할로 남겼습니다.

추가한 패널보이게 한 것
상태 수집 성공 여부 (②)관측 실패와 실행 0건의 구분. 메트릭이 비어도 원인이 둘 중 무엇인지 알 수 있어야 함
활성 DAG/태스크 수, 현재 대기/실행 경과 (①)어떤 작업이 얼마나 기다리고 돌았는지. 끝난 실행의 통계로는 지금 상태가 보이지 않음
DAG별 직전 완료 결과와 신선도 (①)멈춘 파이프라인. 성공 여부만으로는 멈춤이 드러나지 않아, 완료 후 경과 시간으로 드러냄
  • 선택 변수 (③): 등록된 DAG를 선택 변수에 포함해 완료 이력이 없는 백필 DAG도 목록에 나오게 함
  • 시각화 판단: 변수 캐스케이드 $host → $dag_id. 홈서버와 EC2가 서로 다른 DAG를 실행하므로 host를 먼저 골라야 무관한 DAG가 섞이지 않는다

데이터 정합성 대시보드

결과가 맞는지, 얼마나 맞는지, 뭐가 틀렸는지를 점수판 → 게이트 → 추이 → 원시 행 순으로 좁혀 보는 대시보드입니다 (7월 11패널 → 10월 27패널).

지표 선정 근거 (위에서부터 화면 순서)

  1. 최신 DQ 기록 4종 (매핑률, 오류 비중, 카테고리 실패, 카테고리 0건): 알람이 울렸을 때 "왜"를 보는 첫 화면. 단계별 최신 값을 먼저 보고 좁혀 들어가는 구조의 시작점
  2. 게이트 판정, 연속 누락, 부분 수집 입력: 전처리를 진행할지, 경고할지, 멈출지 판단. 연속 누락 수가 곧 데이터 나이 9일 SLO 위반 수
  3. 크롤 수집률 (수집 수 / 기대 URL 수): 카테고리는 "완료"인데 상품이 일부 빠지는 경우를 숫자로 드러냄
  4. 매핑률과 unmatched 건수: 보강이 필요한 규모. unique 성분 대비 매칭 성공/실패 건수를 함께 표시
  5. 입력/정제/오류 레코드 (계산값): 단계별 건수 규모. 정상+오류=입력이 성립하지 않아 보존식이 아닌 참고용 계산값으로 표기

지표를 믿고 읽을 수 있게 한 설계

  • 오류율 → "오류 레코드 비중(참고)": 41%가 상품 실패율로 읽히지 않도록 패널 이름과 설명을 실제 의미에 맞게 바꿈
  • 정상/백필 stage 분리, 추이 x축을 batch_date로 두고 백필은 점선: 오늘 돌린 8월 백필이 "최신 정상 실행"으로 읽히지 않고 8월 위치에 찍힘
  • 집계 완전성 판정: 유형별 합계와 전체 오류 수가 다르면 "집계 불완전"으로 표시. 운영 백필 7건 모두 일치 확인
  • 입력 품질 게이트 행: 판정과 사유 수치 옆에 게이트 로그(Loki)를 붙여 "몇 개"와 "어느 카테고리"를 한 화면에

구조 변경: 로그 파싱에서 테이블로 (1세대 → 2세대)

처음엔 파이프라인 로그의 DQ 값을 LogQL로 파싱했지만, 크롤 호스트가 바뀌면 host 라벨이 갈려 같은 지표가 두 줄로 쪼개지고 배치의 정확한 값까지 내려갈 수 없었습니다. → 품질 지표를 Iceberg 테이블(dq_metrics)로 적재하고 FastAPI + DuckDB로 서빙해, run당 한 행으로 식별하고 원시 행까지 드릴다운합니다.

# 1세대: 로그 파싱 (host가 바뀌면 시계열이 둘로 갈림)
last_over_time({job="airflow", task_id="crawl"} |= `"DQ"`
  | regexp `...` | label_format filename=""
  | unwrap products_total [29d])

# 2세대: 테이블 + API (batch_date, run_id로 한 행)
GET /dq/latest?stage=crawl&metric=products_total

  • 계약 테스트: mock으로 가린 단위 테스트는 통과했음 → 실제 행 값으로 교체와 검증을 확인하는 테스트를 추가하고, 수정 전 코드에서 실패하는지 확인
  • 독립 리뷰: 다른 AI에 검토를 맡겨 지적 반영 (0건 쓰기 전 중단, 정상 실행 중 백필 apply 거부 등)

05 · 베타 운영 (2026.11)

베타 서비스 관측: 트래픽이 거의 없는 서비스의 알림 설계

저트래픽이라 에러율 대신 상시 확인과 사건 수로 설계해, GPU 정지 3회를 모두 3분 만에 감지했습니다.

역할: 앱 개발, 배포, GPU 서버 운영은 팀원 담당. 관측 연결, 알림 설계, 대시보드 보완을 맡음

문제

  • 하루 수십 건 트래픽이라 에러율 같은 비율 알림은 의미가 없음
  • 스트리밍(SSE) 추천은 실패해도 HTTP 200에 event: error로 응답 → 5xx 알림으로는 못 잡는다. 설계 리뷰 중 앱 코드에서 확인하고, 앱이 내보내던 추천 결과 메트릭으로 "추천 실패" 알림을 추가
  • GPU가 꺼지면 앱이 템플릿 응답으로 넘어가 요청은 "성공"으로 기록 → 상시 확인(/ready)만 이 상황을 잡았다

설계 원칙

  • 상시 확인: 요청이 없어도 장애를 잡도록 내부 /ready와 외부 HTTPS를 1분마다 호출
  • 사건 수: 실제 요청은 비율 대신 "1건이라도 생기면" 알림
  • for 시간: 배포 재시작 같은 짧은 끊김은 흡수

관측 구조: 앱 밖으로 분리

처음에는 앱 compose에 수집기(Alloy)를 넣었지만, 운영은 ECR 이미지와 릴리스별 compose 묶음으로 배포되고 있어 설정이 반영될 경로가 없었습니다. 관측을 별도 에이전트 스택으로 분리해 앱의 Docker 네트워크에서 /metrics와 컨테이너 로그를 읽고 Tailscale로 push → 팀원의 앱 레포는 건드리지 않고, 보안그룹에 새 포트도 열지 않았습니다.
